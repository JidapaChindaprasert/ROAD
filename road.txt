# 2. Create `AGENTS.md`

Place this file in the repository root.

```md
# AGENTS.md

## Mission

Build RoadSignal: a polished, accessible, responsive road-damage reporting
and tracking application.

Read SKILL.md completely before implementing.

The deliverable is a functioning application, not a static mockup,
architecture-only response, or collection of disconnected components.

## Working rules

1. Inspect the existing repository before editing.
2. Preserve unrelated user work.
3. Implement in small, testable milestones.
4. Keep docs/IMPLEMENTATION_STATUS.md updated.
5. Prefer straightforward, maintainable solutions over elaborate abstractions.
6. Use strict TypeScript. Avoid `any` unless justified and isolated.
7. Validate all untrusted inputs with Zod or an equivalent explicit validator.
8. Never expose server credentials to client bundles.
9. Never describe mock AI, mock GPS, or simulated realtime as real.
10. Never silently substitute demo data when production services fail.
11. Do not leave dead buttons, broken links, or placeholder interactions.
12. Every visible control must work, be disabled with an explanation,
    or be intentionally omitted.
13. Implement loading, empty, error, permission-denied, and retry states.
14. Do not claim tests passed unless the commands actually ran successfully.
15. Do not claim the app is production-ready solely because it builds.
16. Do not invent external image URLs, map-provider credentials, or API behavior.
17. Use current official documentation when uncertain about a package API.
18. Do not deploy, incur paid usage, or modify remote infrastructure without approval.

## Priority order

1. A fully working demo experience without external credentials.
2. Excellent UI, responsive layout, and accessibility.
3. Correct domain model and repository interfaces.
4. Secure production database, authentication, and authorization.
5. Production upload, geolocation, AI, and realtime integration.
6. Tests, performance validation, and documentation.

## Demo versus production

Demo:
- Runs with NEXT_PUBLIC_APP_MODE=demo.
- Uses deterministic seeded fixtures.
- Persists report changes locally.
- Labels simulated AI and updates.
- Requires no Supabase, AI, or map-provider credentials.

Production:
- Runs with NEXT_PUBLIC_APP_MODE=production.
- Uses authenticated Supabase services.
- Fails clearly when configuration is missing.
- Must not return demo records as if they were production records.

## Framework conventions

- Next.js App Router.
- Server Components by default.
- Client Components only for browser APIs and interactive UI.
- Route handlers for explicit HTTP endpoints.
- Use proxy.ts if required by the installed Next.js version.
- Use @supabase/ssr for Supabase session integration.
- Request interception is not an authorization boundary.
- Check authentication and authorization at the actual data mutation boundary.
- Use the Tailwind conventions generated by the installed major version.
- Do not copy obsolete configuration from older framework versions.

## Required commands

Before declaring completion, run:

- npm run lint
- npm run typecheck
- npm run test
- npm run build
- npm run test:e2e

Run Supabase integration and authorization tests when the local Supabase
environment is available.

If any command cannot run, state the exact reason and remaining risk.

## Definition of done

The product meets the acceptance criteria in SKILL.md, meaningful automated
tests exist, configuration is documented, and no major workflow depends on
unexplained placeholders.

At completion, summarize:
- What was implemented.
- What was tested.
- What is demo-only.
- What requires credentials or infrastructure.
- Any remaining limitations.
```

# 3. Create `SKILL.md`

This is the main implementation specification.

```md
---
name: roadsignal-product-engineering
description: Build a premium road-damage reporting application with AI-assisted classification, location capture, a community map, and transparent tracking.
---

# RoadSignal — Product and Engineering Specification

## 1. Product objective

RoadSignal helps residents report damaged roads in under a minute and
understand what happens after submission.

Core promise:

“Spot it. Report it. Follow the fix.”

Build an actual working application with a premium visual interface and
clear operational boundaries.

The main workflow is:

1. Upload or capture a road image.
2. Request location permission and confirm the reporting position.
3. Show automatic AI-assisted damage classification.
4. Submit the report.
5. Display a public-safe community map entry.
6. Track acknowledgement, assessment, repair, and resolution.

Users must not need to manually type a damage category.

AI may be unavailable or uncertain. Reporting must still work.

## 2. Product identity

Name: RoadSignal

Tone:
- Clear.
- Helpful.
- Trustworthy.
- Contemporary.
- Community-focused.
- Never bureaucratic.

Example interface copy:

- “Better roads start with a signal.”
- “Drop a photo. We’ll help identify the damage.”
- “Location found. Confirm the pin before sending.”
- “Your report is on the map.”
- “The maintenance team has scheduled a repair.”
- “AI needs a clearer image. You can still submit this report.”

Do not imply government affiliation, guaranteed response times,
or emergency dispatch integration.

Include a small safety note:

“Only capture photos when it is safe. Do not use this app while driving.
For immediate danger, contact local emergency services.”

## 3. Technology choices

Use:

- Next.js 16-compatible App Router.
- React version supported by the generated Next.js project.
- TypeScript with strict checking.
- Tailwind CSS.
- Supabase Postgres, Auth, Storage, Realtime, and Edge Functions.
- PostGIS for spatial queries.
- MapLibre GL JS for the production community map.
- TanStack Query for interactive remote state.
- React Hook Form and Zod for validated forms.
- Lucide icons.
- Motion for small, purposeful transitions.
- Sonner for accessible notification feedback.
- Vitest and Testing Library for unit/component tests.
- Playwright and axe for end-to-end and accessibility checks.

AI:
- Implement a server-side provider adapter.
- Use the AI SDK with a compatible vision-capable model.
- Select the model through AI_MODEL.
- Verify the installed AI SDK API.
- For AI SDK 6, prefer structured output through generateText/Output.object
  rather than introducing deprecated generateObject usage.

Avoid:
- Redux unless a concrete requirement emerges.
- Multiple competing component systems.
- Heavy dashboard templates.
- A separate microservice per feature.
- Client-side AI provider credentials.
- Rendering the entire application as one giant client component.

## 4. Required routes

Public:
- /                     Dashboard / product overview.
- /map                  Community map.
- /reports/[id]         Public-safe report detail.

Reporting:
- /report/new           Reporting flow.
- /my-reports           Current user’s reports.

Authentication:
- /login
- /auth/callback

Operations:
- /operations           Staff report queue.
- /operations/reports/[id]

Operational:
- /api/health           Minimal health response without secrets.

Demo mode:
- Reporting and “My reports” work without an external auth provider.
- A clearly identified local demo identity is allowed.
- The operations demo uses an explicitly labelled preview mode.

Production:
- Browsing public reports does not require login.
- Creating persistent reports requires authentication.
- Preserve the local draft through authentication.
- Operations routes require an authorized staff role.

## 5. Visual design direction

### 5.1 Overall aesthetic

Build a premium civic-tech startup interface.

The layout should feel:
- Open.
- Quiet.
- Spatial.
- Precise.
- Friendly.
- Slightly futuristic.

Use:
- Soft off-white backgrounds.
- Deep navy text.
- Bright teal as the main accent.
- Restrained translucent surfaces.
- Thin neutral borders.
- Rounded cards.
- Generous whitespace.
- Crisp typography.
- Subtle map layering.

Avoid:
- Excessive gradients.
- Neon everywhere.
- Heavy dark administrative dashboards.
- Large decorative illustrations.
- Repeated generic statistic cards.
- Dense government-form layouts.
- Emoji as interface icons.

### 5.2 Design tokens

Implement CSS custom properties and map them into Tailwind.

Suggested palette:

--background: #F6F8FB
--surface: #FFFFFF
--surface-muted: #EDF2F7
--text-primary: #132238
--text-secondary: #617086
--border: #E1E8F0

--brand: #087F78
--brand-hover: #06675F
--brand-soft: #E0F5F1
--brand-bright: #37D5BC

--reported: #B45309
--reported-soft: #FFF3D8
--repairing: #4338CA
--repairing-soft: #ECEBFF
--fixed: #047857
--fixed-soft: #DCFCE7
--danger: #B91C1C

Use brand-bright decoratively or with dark text.
Verify all text/background combinations rather than assuming contrast.

Typography:
- Inter if self-hosted or properly bundled.
- Reliable system sans-serif fallback.
- Body text approximately 15–16px.
- Form controls at least 16px on mobile.
- Large page titles with tight but readable tracking.
- Tabular numbers for coordinates and metrics.

Radii:
- Controls: 10–12px.
- Cards: 18–24px.
- Pills: fully rounded.

Shadows:
- Soft, low-opacity, broad shadows.
- Prefer borders and spacing over heavy shadows.

Glass:
- Use selectively on map overlays and navigation.
- Include an opaque fallback.
- Keep content readable over complex map backgrounds.

### 5.3 Layout

Desktop:
- Compact top navigation.
- Centered max-width content area around 1440px.
- 24–32px horizontal gutters.
- Twelve-column main grid.
- Main dashboard content approximately 8 columns.
- Reporting/location side panel approximately 4 columns.
- Large community map.
- Clean activity feed below or alongside the map.

Tablet:
- Two-column layout where space permits.
- Reporting panel can move below the map.

Mobile:
- Single-column layout.
- Compact header.
- Bottom navigation with:
  Home, Map, Report, My reports.
- Report action visually emphasized.
- Map details appear in an accessible bottom sheet.
- Bottom navigation respects safe-area insets.
- No horizontal page overflow.

### 5.4 Motion

Use motion only to clarify state changes.

Examples:
- Upload panel border transition.
- Classification result fade/slide.
- Report marker selection.
- Progress step transition.
- Small success confirmation.

Timing:
- Most transitions: 120–220ms.
- Avoid infinite decorative animation.
- Respect prefers-reduced-motion.

## 6. Dashboard requirements

Header:
- RoadSignal brand mark.
- Overview, Community map, My reports.
- Compact demo/live indicator.
- Primary “Report damage” button.
- User menu or sign-in action.

Hero:
- Eyebrow: “A clearer path forward”.
- Headline: “Better roads start with a signal.”
- Brief explanation.
- Primary action: “Report road damage”.
- Secondary action: “Explore the map”.
- Small trust line describing transparent tracking.

Dashboard content:
- Large community map card.
- Upload shortcut card.
- Current location preview.
- Compact local activity metrics.
- Recent nearby reports.
- Report lifecycle explanation or recent activity feed.

Metrics must be derived from data.
Never display fabricated live claims.

Example demo metrics:
- Open reports.
- Currently repairing.
- Fixed this month.

Label demo data clearly.

## 7. Reporting flow

Use a focused three-step flow:

1. Evidence.
2. Location and review.
3. Submitted.

AI classification appears within this flow; it is not an extra form page.

Preserve draft progress on refresh where reasonable.

### 7.1 Evidence upload

Support:
- JPEG.
- PNG.
- WebP.
- Short MP4 and WebM videos when browser decoding is supported.

Initial limits:
- Maximum 5 files.
- Maximum 10 MB per image.
- Maximum 30 MB per video.
- Maximum 20-second video.
- Maximum 50 MB total per report.

Make limits configurable.

UI:
- Drag-and-drop area.
- File picker.
- Mobile camera capture where supported.
- Thumbnail previews.
- Remove and replace actions.
- Upload progress.
- Per-file errors.
- Retry failed uploads.

Do not promise universal camera or codec support.

When decoding is unavailable:
- Explain the issue.
- Ask the user to upload a supported image.
- Do not let the form hang indefinitely.

Validation:
- Check browser-side limits for immediate feedback.
- Revalidate server-side.
- Inspect file signatures, not only extensions.
- Limit decoded pixel dimensions.
- Reject SVG, executables, and unsupported content.
- Revoke object URLs when no longer needed.

Privacy:
- Remove image metadata during trusted processing.
- Keep raw uploads private.
- Never publish original media by default.

### 7.2 Video handling

Do not imply that a still-image model understands an entire video.

Initial implementation:
- Extract up to 3 representative frames in the browser when supported.
- Present extracted frames as the evidence preview.
- Upload those frames through the normal trusted image pipeline.
- Keep the original video private if retained.
- Label classification as based on sampled frames.

Use a timeout and explicit failure state.

Do not add a heavyweight server-side transcoding stack for the first version.
Document this limitation.

### 7.3 AI damage classification

Component states:
- No evidence.
- Uploading.
- Queued.
- Analyzing.
- Results available.
- Low certainty.
- Unavailable.
- Failed with retry.

Example result presentation:
- Pothole — 98%.
- Crack — 85%.
- Surface wear — 41%.

Important:
- These percentages represent model-reported scores, not validated accuracy.
- Use a tooltip or caption:
  “AI estimate. Not a verified engineering assessment.”
- If the provider does not return meaningful scores, omit percentages.
- Never invent a probability because the design wants a percentage.

Supported categories:
- pothole
- crack
- surface_wear
- subsidence
- obstruction
- standing_water
- other
- uncertain

Possible sinkholes:
- Display as “Possible sinkhole / subsidence”.
- Route for human review.
- Do not treat an image-only result as a confirmed structural diagnosis.

Structured output:
- labels
- primaryCategory
- suggestedSeverity
- summary
- needsHumanReview
- imageQualityIssues

Each label contains:
- category
- optional score between 0 and 1

AI severity:
- low
- medium
- high
- unknown

Operational priority is a separate staff-controlled field.

Users:
- Do not have to type a category.
- May optionally flag “This does not look right”.
- May submit while classification is unavailable or pending.
- Must see whether classification is provisional or reviewed.

Do not fabricate real AI analysis in demo mode.
Use deterministic sample results and a visible “Demo analysis” label.

### 7.4 Optional notes

Provide:
- Optional description.
- Optional location context such as “outside the station entrance”.

Do not require:
- A long narrative.
- A typed damage category.
- A manually entered address if coordinates are available.

## 8. Location capture

### 8.1 Honest permission flow

A website cannot access GPS without browser permission.

Provide a prominent:
“Use my location” button.

After consent:
- Start location acquisition.
- Show acquisition state.
- Show latitude and longitude.
- Show accuracy in meters.
- Show last-updated time.
- Show the pin on a mini-map.

Use:
- getCurrentPosition for initial acquisition.
- watchPosition while the location confirmation panel is active.
- clearWatch on unmount or when location capture is disabled.

Do not continuously track users after submission.

### 8.2 Location states

- Not requested.
- Requesting.
- Acquired.
- Permission denied.
- Timed out.
- Unavailable.
- Low accuracy.
- Manual position selected.

If GPS fails:
- Let the user place a pin manually.
- Permit coordinate entry as an accessible fallback.
- Never block reporting solely because permission was denied.

### 8.3 Exact reporting position

Live device location and confirmed report location are different concepts.

Rules:
- Follow live location until the user confirms or manually moves the pin.
- Once manually adjusted, new GPS readings must not overwrite the choice.
- Show “Return to my location” to opt back in.
- Require confirmation before submission.

Store:
- Exact latitude.
- Exact longitude.
- Accuracy.
- Position source: gps or manual.
- Location capture timestamp.

Coordinates shown to the reporter can be precise.
Public map coordinates must use a privacy-preserving derived location.

### 8.4 Reverse geocoding

Optional enhancement, not a submission dependency.

- Use a configured provider.
- Cache rounded-coordinate results.
- Respect provider limits and licensing.
- Do not call an unrestricted public geocoder on every GPS update.
- Do not expose private API keys.
- If unavailable, display coordinates instead of a fabricated address.

## 9. Community map

### 9.1 Production map

Use MapLibre GL JS with a configured licensed map style.

Load the interactive map client-side.
Do not block the first render on the map bundle.

Required behavior:
- Pan and zoom.
- Cluster markers at low zoom.
- Show individual markers at high zoom.
- Filter by status and damage category.
- Select a marker.
- Open a report preview.
- Navigate to report detail.
- Recenter using explicit user permission.
- Reset filters.
- Switch between map and accessible list view.

Optional but desirable:
- Density/heatmap toggle.
- Time-range filter.
- Search by configured geocoding provider.

If heatmap mode is implemented:
- Describe it as report density.
- Do not call it a verified danger map.
- Do not imply density equals road severity.

### 9.2 Status visuals

Public status groups:
- Reported: amber dot plus label.
- Repairing: indigo tool icon plus label.
- Fixed: green check plus label.

Detailed status appears in the report panel.

Do not use color as the sole status indicator.

### 9.3 Map interactions

Desktop:
- Floating filters.
- Map controls in a consistent corner.
- Selected report preview anchored beside or above the map.

Mobile:
- Filter sheet.
- Report detail bottom sheet.
- Accessible dismissal.
- No accidental conflict with bottom navigation.

Prefer MapLibre layers over hundreds of React DOM markers.

### 9.4 Queries

Fetch by visible map bounds.

- Debounce viewport requests.
- Cancel obsolete requests.
- Cap results.
- Paginate the companion list.
- Handle antimeridian bounds correctly or document and enforce a
  deliberately limited supported region for the first release.
- Use a spatial index.
- Use a minimum movement/zoom threshold before refetching.

Do not fetch every report in the database on each map movement.

### 9.5 No-key demo map

The app must look complete without a map-provider credential.

Provide a self-contained schematic city map:
- Drawn with local SVG.
- Seeded road lines, blocks, and river/canal shapes.
- Clickable report markers.
- Working status filters.
- Working marker selection.
- Clearly labelled “Demo city map — schematic”.

This is not a real basemap and must not be presented as one.

When a production map style is unavailable:
- Show a clear configuration message.
- Keep the accessible report list available.
- Never silently show a schematic as real geographic data.

## 10. Transparent report tracking

### 10.1 Canonical lifecycle

Use these internal statuses:

- reported
- acknowledged
- assessing
- scheduled
- repairing
- resolved
- rejected
- duplicate

Public mapping:
- Reported:
  reported, acknowledged, assessing, scheduled
- Repairing:
  repairing
- Fixed:
  resolved

Rejected and duplicate remain distinct and visible where appropriate.

### 10.2 Timeline

Show chronological events:
- Report submitted.
- Report acknowledged.
- Assessment started.
- Repair scheduled.
- Repair in progress.
- Repair completed.

Each event may contain:
- Timestamp.
- Public note.
- Responsible team display name.
- Optional scheduled date.
- Optional resolution evidence.

Do not invent an estimated repair date.
Show “Not scheduled yet” if no schedule exists.

Timeline events must be server-generated and append-only.

### 10.3 Reopening

Support a controlled staff transition:
- resolved → assessing

Require a reason.
Append a reopening event.
Never delete the original resolution history.

### 10.4 Staff operations

Provide a real minimal operations interface.

Capabilities:
- Filter and inspect incoming reports.
- See exact coordinates when authorized.
- Inspect private evidence when authorized.
- Review AI suggestions.
- Set operational priority.
- Assign a team.
- Add public or internal notes.
- Change status through permitted transitions.
- Mark duplicates using a canonical report ID.
- Add resolution evidence.

Reporter users cannot perform these actions.

Internal notes must never appear in public API responses.

## 13. Privacy and authorization

### 13.1 Public location

Public locations should be snapped or generalized to approximately
a 30–50 meter grid, with the limitation explained.

Keep exact report coordinates available only to:
- The report owner.
- Authorized staff.

Use an appropriate projected/local-meter approach.
Do not assume an arbitrary decimal truncation is uniformly measured in meters.

### 13.2 Public map projection

Keep public data separate from private report rows.

Prefer:
- An explicitly sanitized projection table.
- Or a carefully secured RPC returning only allowed columns.

Avoid casual use of views that bypass underlying row-level security.
Verify the actual security behavior of the chosen view/RPC approach.

### 13.3 RLS policies

At minimum:

Profiles:
- Users read/update permitted fields on their own profile.

Drafts:
- Owners access their own drafts.

Reports:
- Owners read their own reports.
- Staff access reports within their role.
- Public visitors access only the public-safe projection.

Media:
- Owners access their own evidence.
- Authorized staff access evidence.
- No default public listing.

AI:
- Owners and staff access relevant analysis.
- Public output only through reviewed/sanitized fields.

Events:
- Users cannot forge operational timeline events.
- Public sees only public fields.

Roles:
- Normal users cannot mutate authorization roles.

Jobs:
- No client read/write access.

### 13.4 Mutations

Use narrowly scoped transactional functions or server operations.

Status transitions must:
- Verify the actor.
- Verify their role.
- Validate the transition.
- Compare the expected report version.
- Update status and version.
- Append a timeline event.
- Update the public-safe projection.
- Commit atomically.

Use the ordinary user session for ordinary user requests.

Service-role credentials are reserved for trusted processing jobs and
explicitly justified maintenance operations.

A service-role client must not become a shortcut around authorization.

### 13.5 Media privacy

Original uploads remain private.

Public images:
- Disabled by default in the initial release.
- May be enabled only after moderation and appropriate redaction.
- Never assume stripping EXIF removes faces, license plates, or house details.

Use expiring signed URLs for authorized private viewing.

Do not log:
- Signed URLs.
- Raw GPS coordinates.
- Access tokens.
- Uploaded image bodies.
- AI provider credentials.

## 14. Backend workflow

### 14.1 Draft and upload

1. Authenticated user creates a draft.
2. Server issues a scoped upload intent.
3. Browser uploads directly to a private storage object.
4. Browser calls finalize-upload.
5. Server verifies object ownership and metadata.
6. Server enqueues a media-processing job.
7. A worker validates and sanitizes the image.
8. A classification job is enqueued for eligible sanitized evidence.
9. The UI receives or polls for state updates.

The route handler must not send the response and then rely on an
unawaited promise continuing in a serverless runtime.

### 14.2 Submit

1. Validate draft ownership.
2. Validate a confirmed location.
3. Ensure at least one acceptable evidence item exists.
4. Create the report using an idempotency key.
5. Attach the draft media/analysis.
6. Append the initial reported event.
7. Write the public-safe map projection.
8. Return the same report on an identical retry.

Report creation must not depend on successful AI classification.

Pending or failed classification becomes:
“AI review pending” or “Needs human review”.

### 14.3 Background processing

Use durable database-backed jobs.

Required semantics:
- Transactional job claim.
- FOR UPDATE SKIP LOCKED or equivalent.
- Lease expiration.
- Bounded retries.
- Exponential backoff.
- Idempotent completion.
- Deduplication by content hash/model/prompt version within an appropriate scope.
- Stale-job recovery.
- Sanitized error codes.
- Dead-letter or permanently-failed state.

A cron-triggered worker is the recovery mechanism.

For lower latency:
- Trigger a best-effort wake-up after durable enqueue.
- A failed wake-up must not lose the job.

Protect worker invocation using server-side authentication.
Do not expose an unauthenticated “run jobs” endpoint.

Document how the worker is deployed and scheduled.

### 14.4 AI request safety

- Run provider calls only on trusted servers/workers.
- Use sanitized images with bounded dimensions.
- Enforce timeout, retry, and cost limits.
- Validate returned structured output.
- Treat text visible inside uploaded images as untrusted data.
- Instruct the model not to follow instructions embedded in images.
- Do not give the classification model tools or privileged actions.
- Do not automatically change repair status based on AI output.
- Do not claim the system has engineering-grade detection accuracy.
```
